# PAI Webhook Bridge - Design Spec

## Overview

A separate Docker microservice that subscribes to PAI's MQTT topics and forwards matching messages as HTTP POST webhooks to a custom endpoint. Built with async Python (paho-mqtt + aiohttp).

## Problem

PAI exposes alarm panel state and events via MQTT. Some integrations need HTTP webhooks instead of maintaining an MQTT subscription. This bridge converts MQTT messages into HTTP POST calls with configurable topic filtering and retry logic.

## Architecture

```
MQTT Broker (PAI publishes) ──subscribe──> pai-webhook daemon ──POST──> Custom HTTP Endpoint
                                                 |
                                            /health (GET)
```

Single async Python process with three components:

1. **MQTTSubscriber** - connects to MQTT broker, subscribes to configured topic patterns, pushes received messages into a bounded asyncio queue
2. **WebhookDispatcher** - reads from queue, POSTs JSON to configured endpoint, retries with exponential backoff on failure
3. **HealthServer** - aiohttp server exposing `GET /health` for container orchestration

## PAI MQTT Topic Structure

PAI publishes to these topic patterns (base topic default: `paradox`):

- `paradox/states/{element_topic}/{label}/{property}` - state changes (zones, partitions, outputs, doors, users, etc.)
- `paradox/events/raw` - raw event JSON (alarm triggers, arm/disarm, troubles, tampers)
- `paradox/interface/pai_status` - PAI connection status (initializing, running, error, stopped)
- `paradox/interface/availability` - online/offline

## Config File (`config.yaml`)

```yaml
mqtt:
  host: "<mqtt-broker-host>"
  port: 1883
  username: "<mqtt-username>"
  password: "<mqtt-password>"
  client_id: pai-webhook
  qos: 1                          # Subscribe QoS: 0=fire-and-forget, 1=at-least-once (default), 2=exactly-once
  clean_session: true              # true=no stored messages while offline, false=broker queues missed messages
  topics:
    - "paradox/states/#"
    - "paradox/events/#"

webhook:
  url: "https://your-endpoint.example.com/alarm"
  headers:                         # Additional headers sent with each POST (Content-Type: application/json is always set)
    Authorization: "Bearer <your-token>"
  timeout: 10
  retry:
    max_attempts: 3
    backoff_base: 2                # Delay formula: backoff_base^(attempt-1) seconds, e.g. 2s, 4s, 8s

health:
  port: 8080

logging:
  level: INFO
```

## Webhook Payload Format

Each MQTT message becomes a `POST` with `Content-Type: application/json`. The `Content-Type` header is always set automatically and cannot be overridden via config.

Timestamps are always UTC, formatted as ISO 8601 with microseconds: `%Y-%m-%dT%H:%M:%S.%fZ`. The timestamp records when the bridge received the MQTT message.

### State changes (string payloads)

```json
{
  "source": "pai",
  "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "topic": "paradox/states/zones/Front_Door/open",
  "payload": "True",
  "timestamp": "2026-03-14T10:30:45.123456Z"
}
```

### Raw events (JSON payloads)

When the MQTT payload is valid JSON (e.g. from `paradox/events/raw`), it is parsed and nested as an object. Note: the raw event payload structure comes from PAI's `Event.props` and includes all non-private attributes (type, label, major, minor, timestamp, message, tags, level, change, additional_data, module, partition, label_type, etc.). The example below is illustrative - actual payloads may contain more or fewer fields depending on event type:

```json
{
  "source": "pai",
  "id": "b2c3d4e5-f6a7-8901-bcde-f12345678901",
  "topic": "paradox/events/raw",
  "payload": {
    "type": "zone",
    "label": "Front Door",
    "major": 1,
    "minor": 2,
    "partition": 1,
    "module": 0,
    "level": "CRITICAL",
    "timestamp": "2026-03-14T10:30:45",
    "message": "Zone Front Door open",
    "tags": ["live", "alarm"],
    "change": {"open": true},
    "additional_data": {}
  },
  "timestamp": "2026-03-14T10:30:45.123456Z"
}
```

The `id` field is a UUID v4 generated by the bridge for each message. Receivers can use this for deduplication (relevant when MQTT QoS >= 1, which may deliver duplicates).

## Components

### MQTTSubscriber (`mqtt_subscriber.py`)

- Uses `paho-mqtt` (same library as PAI)
- Connects with configurable host/port/credentials
- Subscribes to all topics listed in `config.mqtt.topics` at the configured QoS level
- Uses `clean_session` setting from config (default `true`)
- **Threading boundary**: paho-mqtt's `on_message` callback runs on paho's network thread, not the asyncio event loop. The subscriber uses `loop.call_soon_threadsafe(queue.put_nowait, envelope)` to safely pass messages from paho's thread to the asyncio queue. This is the only point where the two threading models interact.
- On message received: creates envelope dict (`source`, `id`, `topic`, `payload`, `timestamp`) and passes it to the asyncio queue via `call_soon_threadsafe`
- Attempts JSON parse of payload; if valid JSON, nests as object; otherwise keeps as string
- Reconnects automatically on broker disconnect (paho-mqtt handles this)

### WebhookDispatcher (`webhook_dispatcher.py`)

- Reads from asyncio queue in a loop
- POSTs JSON envelope to `config.webhook.url` with `Content-Type: application/json` (always set, not overridable) plus any additional headers from config
- On success (2xx): log and continue
- On failure (non-2xx, timeout, connection error): retry with exponential backoff
  - Retry delay formula: `backoff_base ^ (attempt - 1)` seconds (attempt 1 is immediate, attempt 2 waits `backoff_base` seconds, attempt 3 waits `backoff_base^2` seconds, etc.)
  - Jitter: add random 0-1s to each delay to avoid thundering herd on recovery
  - After `max_attempts` failures: log error at WARNING level, drop message, continue
- Uses `aiohttp.ClientSession` for connection pooling
- **Queue overflow**: the queue is backed by `asyncio.Queue(maxsize=10000)`. When full, `put_nowait` raises `QueueFull`. The subscriber catches this, calls `queue.get_nowait()` to discard the oldest item, logs a warning, then retries `put_nowait` with the new message. This ensures the queue always has the most recent messages.

### HealthServer (`health.py`)

- `aiohttp` web server on configured port (default 8080)
- `GET /health` returns:
  - `200 {"status": "ok", "mqtt_connected": true, "queue_size": 5, "last_webhook_success": "2026-03-14T10:30:00Z", "last_webhook_failure": null}` when healthy
  - `503 {"status": "unhealthy", "mqtt_connected": false, ...}` when MQTT is disconnected
- `last_webhook_success` and `last_webhook_failure` are ISO 8601 timestamps of the most recent successful/failed webhook delivery (null if none yet)
- Used by Docker healthcheck and orchestration tools

### Config (`config.py`)

- Loads YAML from path (default `/app/config.yaml`, overridable via `PAI_WEBHOOK_CONFIG` env var)
- Validates required fields (mqtt.host, mqtt.topics, webhook.url)
- Provides typed access to config values with sensible defaults:
  - `mqtt.qos`: 1
  - `mqtt.clean_session`: true
  - `webhook.timeout`: 10
  - `webhook.retry.max_attempts`: 3
  - `webhook.retry.backoff_base`: 2
  - `health.port`: 8080
  - `logging.level`: INFO

### Main (`main.py`)

- Entry point: loads config, creates components, runs asyncio event loop
- Wires: MQTTSubscriber -> asyncio.Queue(maxsize=10000) -> WebhookDispatcher
- Starts HealthServer concurrently
- Handles SIGINT/SIGTERM for graceful shutdown

## Dockerfile

```dockerfile
FROM python:3.12-alpine
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY pai_webhook/ pai_webhook/
COPY config.yaml .
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s CMD wget -qO- http://localhost:8080/health || exit 1
CMD ["python", "-m", "pai_webhook.main"]
```

## docker-compose.yaml

The compose file assumes an external MQTT broker (PAI's broker or a standalone one). Adjust `mqtt.host` in config.yaml to match your broker address.

```yaml
services:
  pai-webhook:
    build: ./pai-webhook
    volumes:
      - ./pai-webhook/config.yaml:/app/config.yaml:ro
    ports:
      - "8080:8080"
    restart: unless-stopped
```

## Error Handling

- MQTT disconnect: paho-mqtt reconnects automatically; HealthServer reports `mqtt_connected: false`
- Webhook target down: retry with backoff + jitter, drop after max_attempts
- Queue overflow (10k messages): discard oldest message, log warning, accept new message
- Invalid config: fail fast at startup with clear error message
- Malformed MQTT payload: forward as-is (string), log at debug level

## Logging

- Structured log lines with timestamp, level, component
- Default level: INFO
- DEBUG: every MQTT message received, every webhook attempt
- INFO: startup, shutdown, MQTT connect/disconnect, webhook delivery success
- WARNING: retry attempts, queue overflow drops, message drops after max retries
- ERROR: config validation failure, unhandled exceptions

## Graceful Shutdown

On SIGINT/SIGTERM:
1. Stop accepting new MQTT messages (disconnect MQTT client)
2. Drain remaining queue items with a **30-second timeout** (attempt delivery, respect retry policy; after 30s discard remaining and log count)
3. Close aiohttp session
4. Exit

## Known Limitations (v1)

- **No MQTT TLS**: v1 does not support TLS for the MQTT connection. If your broker requires TLS, this must be added before deployment. Could be added as `mqtt.tls.ca_cert` config field in a future version.
- **No payload filtering**: all messages matching subscribed topics are forwarded. Topic-level filtering is available via config, but there is no content-based filtering (e.g. "only forward alarm events, not heartbeats"). This can be added as a `webhook.filters` config section in v2.
- **In-memory queue only**: the retry queue is in-memory. If the bridge process crashes, queued messages are lost. For guaranteed delivery, a persistent queue (SQLite, Redis) would be needed.
